# tymbaca.space

Персональный блог на SvelteKit. Статьи лежат в папке `contents` внутри git-репозитория, читаются с диска на каждом запросе и не требуют перезапуска сервера при добавлении или редактировании.

## Быстрый старт

Нужен Node.js **22.17+** (так требует SvelteKit 3).

```bash
npm install
npm run dev
```

- `/articles` — список статей;
- `/article/<slug>` — статья;
- `/` — редирект на `/articles`.

## Как устроен контент

```
contents/
  test-article/
    main.md          # текст статьи
    md.json          # дата, теги, черновик
    include/
      photo.jpg
      Counter.svelte
```

### `main.md`

Заголовок статьи — **первая непустая строка файла**. Если она начинается с `#`, символы решётки отрезаются:

```md
# Как устроен блог

Текст статьи…
```

В списке будет «Как устроен блог». Первая строка считается заголовком и в теле статьи не дублируется — оно начинается со следующей строки.

### `md.json`

```json
{
  "created_at": "2026-11-08",
  "updated_at": "2026-11-09",
  "tags": ["svelte", "notes"],
  "draft": false
}
```

- `created_at` — дата в списке и сортировка (по убыванию);
- `updated_at` — необязательная дата обновления;
- `tags` — массив тегов (можно строку через запятую);
- `draft: true` — статья скрыта, пока не задан `SHOW_DRAFTS=true`.

Папки, начинающиеся с `_` или `.`, не показываются.

### Добавление статьи без перезапуска

Создайте папку, например `contents/hello-world/`, положите туда `main.md` и `md.json`, обновите страницу — статья появится в списке. Сервер читает файловую систему на каждом запросе, поэтому не нужны ни пересборка, ни рестарт. Это работает и в dev, и в production (`node build`).

Скрытые служебные папки: `node_modules`, `.svelte-kit`, `build` — контентом не считаются, потому что статьи берутся только из `contents`.

## Markdown и инклюды

Поддерживается GitHub Flavored Markdown: таблицы, чекбоксы, зачёркивание, автолинки. Код подсвечивается Shiki, у заголовков есть якоря, у блоков кода — кнопка копирования, справа строится оглавление.

ID заголовков генерируются в GitHub-стиле: `## Block Elements` → `#block-elements`, `### Headers` → `#headers`. Если в статье есть ручное оглавление, ссылки в нём должны совпадать с этими ID — старые якоря вроде `#header` или `#block` не найдут элемент и не прокрутят страницу.

### Картинки и файлы

Пути считаются относительно папки статьи:

```md
![](include/photo.jpg)
[Скачать PDF](include/report.pdf)
```

Такие ссылки переписываются на `/content/<slug>/...` и раздаются серверным роутом. Выйти за пределы папки статьи через `../` нельзя.

### Svelte-компоненты

Компонент подключается как обычная картинка:

```md
![](include/Counter.svelte)
```

Компонент получает пропсы из query-строки. Значения приводятся к числам/булевым/JSON, где это возможно:

```md
![](include/Counter.svelte?start=5&step=2&label=Likes)
```

Если проп `label` не задан, в него попадёт alt-текст картинки.

Что происходит под капотом:

1. сервер находит `.svelte`-файл внутри папки статьи;
2. компилирует его через `svelte/compiler` в клиентский код;
3. `esbuild` собирает компонент вместе с его копией Svelte runtime в один ES-модуль;
4. браузер загружает `/components/...` и монтирует компонент в плейсхолдер.

Поэтому компонент может быть добавлен или изменён на работающем сервере: при обновлении страницы версия файла (mtime + размер) меняется, и браузер загружает свежий модуль. Компиляция кешируется по mtime.

Ограничения и детали:

- компонент рендерится **на клиенте** после гидратации; до этого виден плейсхолдер «Interactive component»;
- стили компонента инжектируются самим Svelte (компиляция с `css: 'injected'`);
- поддерживается `<script lang="ts">` — Svelte 5 умеет разбирать TypeScript;
- относительные импорты и npm-пакеты внутри компонента работают (esbuild резолвит их от папки компонента);
- SvelteKit-специфичные виртуальные модули вроде `$app/*` внутри контентных компонентов не поддерживаются;
- markdown и компоненты — доверенный код владельца сайта. HTML в markdown не санитизируется, а компоненты исполняют JS в браузере. Не давайте доступ к редактированию контента недоверенным людям.

## Production

Сборка:

```bash
npm ci
npm run build
```

Запуск из корня репозитория (важно: `contents` ищется относительно `process.cwd()`):

```bash
node build
```

Переменные окружения:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `PORT` | `3000` | порт adapter-node |
| `ORIGIN` | — | публичный URL для корректных редиректов/форм |
| `CONTENT_DIR` | `contents` | папка со статьями относительно рабочей директории |
| `SHOW_DRAFTS` | `false` | `true`, чтобы показывать черновики |
| `BACKEND_URL` | `http://localhost:8080` | адрес HTTP-шлюза бэкенда, куда проксируются просмотры статей |

Для работы сервера в рантайме нужны production-зависимости (`svelte/compiler`, `esbuild`, markdown-пайплайн). Ставьте их на сервере (`npm ci --omit=dev` после сборки) или оставьте `node_modules` целиком.

### Деплой-сценарий

1. На сервере в рабочей директории процесса лежит этот git-репозиторий.
2. Один раз выполняется `npm ci && npm run build`.
3. Процесс запускается как `node build` (systemd, pm2, Docker — на ваш выбор).
4. Дальше вы редактируете `contents` прямо в репозитории: `git pull`, или создаёте файлы вручную. Перезапуск не нужен; изменения подхватываются на следующем запросе страницы.
5. Если менялся код самого приложения (не контент), нужен `npm run build` и рестарт процесса.

## Полезные команды

```bash
npm run check    # svelte-check + TypeScript
npm run build    # production-сборка в build/
npm start        # node build
```

## Тема

По умолчанию включена тёмная тема. Переключатель — кнопка с солнцем/луной в шапке; выбор сохраняется в `localStorage` под ключом `theme` и применяется до первой отрисовки, без мигания. Светлая тема включается той же кнопкой.

## Где что менять

- тексты интерфейса, имя сайта — `src/lib/config.ts`;
- дизайн-токены, шрифт и палитры тёмной/светлой темы — `src/app.css`;
- парсинг статей — `src/lib/server/content.ts`;
- markdown-пайплайн и инклюды — `src/lib/server/markdown.ts`;
- рантайм-компиляция Svelte — `src/lib/server/svelte-compiler.ts`.
