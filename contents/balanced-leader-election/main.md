# Balanced Leader Election

## Leader election
Leader election - процесс, когда несколько нод решают кто из них лидер. 

```go
type Election interface {
    IsLeader() bool
}
```

Алгоритмов leader election'а есть много, но в рамках привычной продуктовой разработки 
я в основном сталкивался с таким:
- Раз в `N` секунд каждая нода обращается к общему хранилищу и пытается проставить
  туда (под определенный ключ) свой ID с `T` TTL'ем ЕСЛИ там еще нет чужой записи:
  - Если не получилось (кто-то другой успел проставить раньше) - нода идет на ретрай;
  - Если получилось - нода становится лидером. Теперь она каждый `M` секунд
    обращается к хранилищу и продлевает TTL;
  - Если лидер упал или потерял связь с базой, то через некоторое время его
    запись в базе протухнет и лидерство заберет другая реплика.

Это, по-умному, называется ***lease-based leader election***. Это довольно простой
алгоритм, не требующий, чтобы ноды знали друг о друге, что хорошо подходит для
привычных stateless приложений.

Зачем? В типичных продуктовых приложениях можно встретить cron-джобы -
асинхронные воркеры, выполняющую какую-то логику с определенной периодичностью.
Например: `CancelOutdatedOrdersJob`. 

Так вот, часто нам достаточно, чтобы эта джоба запускалась лишь в одном
экземпляре, на одной ноде: если одна нода отменит старые заказы - другим нодам
нет смысла делать то же самое параллельно. И с этим помогает leader election:
джобу будет выполнять тот, кто держит лидерство.

```go
if election.IsLeader() {
    CancelOutdatedOrdersJob.Run()
}
```

Чем это чревато?

В нашем приложении может быть много фоноввых джоб, требующих такую дедупликацию. 
Мы можем пойти двумя путями:
- Использовать один _election-ключ_ на все джобы. В таком случае все джобы
  будут выполняться на одном инстансе;
- Использовать множество election-ключей, по одному на каждую джобу. В
  таком случае лидерство может раскидаться рандомно по всем инстансам. Либо все
  лидерства уйдет в один инстанс, если по какой-то причине остальные ноды
  задержались


Первый вариант может нам не подойти, особенно в случае когда большая часть
работы нашего приложения заключена в крон-джобах. Потому что всю работу будет
выполнять одна нода, а остальные будут простаивать, удерживая память и цпу.

Если же мы попытаемся сбалансировать лидерство пойдя вторым путем (грязный хак) - 
то довольно быстро поймем, что это не лучший вариант. Наши реплики редко
стартуют одновременно (точнее, почти никогда). А значит и лидерство почти всегда
будет уходить в одну ноду и не будет нормально и предсказуемо балансироваться.

## Надо как-то балансировать

Перейду сразу к делу. Для балансировки нужно добавить дополнительный слой 
управления над нашим алгоритмом - `Balancer`. Делать он будет следующее:
- Нода узнает из хранилища текущее:
  - количество активных нод,
  - количество ключей (джоб), которые удерживает эта нода,
- Если количество удерживаемых ключей превышает `M = ceil(L/C)` (где `L` это
  общее количество ключей/джоб, `C` это количество активных нод, а `ceil` - округление вверх), 
  то текущая нода *сбрасывает* некоторое количество ключей (***lease shedding***), чтобы
  количество удерживаемых ключей сравнялось с `M`.
